# เช็คชื่อกิจกรรมรายวัน — เตรียมในเครื่อง 25 ตุลาคม 2569

## การใช้งาน

ในปฏิทิน กดเพิ่มกิจกรรมหรือแก้รายการ เลือกวันที่ตั้งค่า แล้วค้นหา/กรองฝ่ายเพื่อเลือกสมาชิกเฉพาะวันนั้น เลือกต้องเช็คชื่อหรือยกเว้นทั้งวัน หากต้องเช็คชื่อให้ระบุเปิดรับ เริ่มสาย และปิดรับ ใช้ปุ่มคัดลอกเพื่อเริ่มจากกติกาเดียวกันทุกวันแล้วปรับบางวันได้ ส่วนสรุปแสดงรายชื่อและเวลาครบก่อนบันทึก

สิทธิ์จัดการใช้ของเดิม: ผู้ดูแล ประธาน และฝ่ายปกครอง สมาชิกทั่วไปอ่านกติกาของตนและเช็คชื่อได้ ไม่สามารถแก้รายชื่อหรือเรียก API แทนผู้อื่น

## กติกา

- ผู้ไม่มีรายชื่อใช้เช็คชื่อปกติ คนที่มีรายชื่อใช้กติกากิจกรรมแทน ไม่ได้เช็คเพิ่มเป็นรอบที่สอง
- เปิดรับและปิดรับรวมจุดเวลาตรงขอบ เริ่มคิดสายเมื่อเลยเวลาเริ่มสายตามวินาทีบนเซิร์ฟเวอร์ ใช้ `ceil` เป็นนาทีและอัตราเดิม 5 บาท/นาที ฝ่ายปกครองสองเท่า
- หลังปิดไม่มีผลเช็คชื่อจะแสดงขาดในรายงานเพื่อพิจารณา ไม่เขียนค่าปรับขาดอัตโนมัติ รายงานประเมินสถานะจากกติกาและผลที่บันทึก ไม่ต้องเปิดหน้าสมาชิกให้เกิดค่าปรับ
- ยกเว้นเช็คชื่อหมายถึงเช็คชื่อประจำวัน ไม่ยกเว้นเวรไหว้/เวรห้องสภาโดยอัตโนมัติ
- ในโรงเรียนต้องส่ง GPS และผ่านรัศมีโรงเรียนที่ตรวจซ้ำบนเซิร์ฟเวอร์ นอกสถานที่ข้าม GPS ทั้งสองกรณีถ่ายภาพผ่านขั้นตอนเดิม พิกัดจากอุปกรณ์ไม่ใช่หลักฐานต้านการปลอม GPS
- วันหยุดหรือวันไม่เปิดปกติใช้กติกากิจกรรมเฉพาะผู้มีชื่อได้ การปิดระบบทั้งหมดมีผลเหนือกิจกรรม
- แต่ละคนมีหนึ่งกิจกรรมต่อวัน บันทึกกิจกรรมกับรายชื่อในธุรกรรมเดียว ใช้ unique constraint และ lock ร่วมกับเช็คชื่อ ปฏิเสธวันที่ผ่านมา/สมาชิกที่มีผลแล้วเมื่อกติกาเปลี่ยน ไม่ลบผลและค่าปรับเก่า

## Backend ที่เตรียม

Migration `20261025154029_daily_event_attendance.sql` เพิ่มกติการายวัน รายชื่อรายวัน และ snapshot กติกาบนผลเช็คชื่อ เก็บ snapshot สมาชิกของกิจกรรมก่อน migration เพื่อรักษาการยกเว้นย้อนหลัง แล้วตรวจความซ้อนก่อนย้ายเฉพาะวันนี้และอนาคต

- `save_council_event` เพิ่ม `p_days` เป็น JSON array ข้อมูลแต่ละวัน: date, mode (`check`/`exempt`), opens_at, late_at, closes_at และ participants เป็น UUID array คำขอสามพารามิเตอร์เดิมยังแปลงเป็นรายชื่อ/เวลาเดียวทุกวันได้
- `get_event_attendance_editor` ส่งกติกา รายชื่อและสถานะล็อกให้ผู้จัด
- `get_my_checkin_context` ส่งกติกาของเจ้าของบัญชีวันนี้ รวมเวลารับ ชื่อกิจกรรม GPS และสถานะปัจจุบัน
- `record_my_checkin` รับภาพกับพิกัดเพิ่มแบบ optional คำขอภาพอย่างเดียวของการเช็คชื่อปกติใช้ได้ตามเดิม แต่กิจกรรมในโรงเรียนต้องใช้เว็บรุ่นใหม่ที่ส่งพิกัด
- `get_my_event_attendance` ใช้ประวัติส่วนตัว และ `get_event_attendance_report` จำกัดให้ผู้จัดปฏิทิน/ฝ่ายปกครอง

หน้าเช็คชื่อ หน้าหลัก ประวัติส่วนตัว รายงานฝ่ายปกครอง และรายชื่อที่แสดงในปฏิทินเชื่อมกับกติการายวันแล้ว หน้าเว็บเก่าที่ยังไม่รองรับพิกัดกิจกรรมต้องรีเฟรชหลังเปิดใช้

Apps Script เตรียมให้เตือนกิจกรรมในหน้าต่างเวลาของแต่ละงานแม้อยู่นอกช่วงเข้าแถวปกติ แยกผู้มีชื่อออกจากการเตือนเข้าแถวปกติและไม่เตือนคนยกเว้น/คนเช็คชื่อแล้ว ใช้ trigger ทุก 10 นาทีเดิม เก็บกุญแจป้องกันส่งซ้ำเฉพาะเมื่อ OneSignal รับงานสำเร็จ อาจเตือนช้าตามรอบ trigger และไม่รับประกันว่าโทรศัพท์แสดง push หากอุปกรณ์ไม่อนุญาต

## ตรวจรับ

- `node tests/event-attendance-db.mjs`: ใช้ migration และฟังก์ชันจริงบน PGlite จำลอง ตรวจบันทึก/อ่านรายวัน รายชื่อซ้อนและ rollback เวลาเปิด/เริ่มสาย/ปิด พิกัดผิด วันยกเว้น ระบบปิด กิจกรรมวันไม่เปิดปกติ อัตราปรับเดิมและฝ่ายปกครองสองเท่า การกดซ้ำ ล็อกการแก้/ลบ สิทธิ์ API และ snapshot ย้อนหลัง
- `node --test tests/event-attendance.test.mjs`: ช่วงวัน เวลาแยกวัน การตรวจรายชื่อ และ Apps Script จำลอง (ไม่มีการส่งข้อความจริง)
- `node tests/event-attendance-browser.mjs`: API จำลองทั้งหมด เลือกรายชื่อ คัดลอกแล้วแก้รายวัน โหมดไม่เช็คชื่อ payload ที่บันทึก และหน้าเช็คชื่อก่อนเปิด/ยกเว้น/หลังปิด ตรวจ 320, 390, 768, 1440 px และแนวนอน ไม่ส่งคำขอเขียนไป Supabase/Drive จริง
- Build ผ่าน และ ESLint โมดูลใหม่รวม Calendar/Auth/CheckIn/MyAttendance ผ่าน หน้า Dashboard/Discipline ยังมี lint เดิมนอกส่วนงานนี้ ไม่ได้ล้างโค้ดทั้งไฟล์

## เปิดใช้แยกภายหลัง

ตรวจข้อมูลจริงแบบอ่านอย่างเดียว ณ วันที่ 25 ตุลาคม 2569: ไม่พบรายชื่อกิจกรรมอนาคตซ้อน (0 รายการ) และไม่พบช่วงเวลาเก่าที่ตรวจไม่ผ่าน (0 รายการ) ตารางรายวันยังไม่ได้ติดตั้ง ต้องตรวจซ้ำตอนเปิดใช้เพราะข้อมูลอาจเปลี่ยนได้

ยังไม่ apply migration, ไม่อัปเดต Apps Script จริง, ไม่ deploy เว็บ และไม่สร้างกิจกรรม ผลเช็คชื่อ ค่าปรับ หรือแจ้งเตือนทดสอบในระบบจริง

1. รัน `supabase/event_attendance_preflight.sql` แบบอ่านอย่างเดียวและแก้รายการชน/ช่วงเวลาเก่าไม่ถูกต้องก่อน ไม่เลือกผู้ชนะหรือทิ้งสมาชิกเอง
2. ตรวจ migration กับ schema จริงและใช้งานเฉพาะ migration นี้ อย่า push migration อื่นที่ค้างโดยไม่ได้ตรวจ
3. ประสานอัปเดต SQL กับเว็บรุ่นใหม่ก่อนเริ่มตั้งกติกากิจกรรมจริง แล้วอัปเดต Apps Script และตรวจ trigger สิทธิ์ service role/OneSignal เดิม
4. ทดลองด้วยบัญชีทดสอบที่ได้รับอนุญาตก่อนใช้กับสมาชิกจริง โดยเฉพาะ GPS มือถือ การแสดงผล push และการเช็คชื่อแข่งกับการแก้รายชื่อ

ผลในเครื่องไม่ยืนยันการส่ง push จริง การถ่ายภาพ/GPS บนอุปกรณ์จริง หรือการทำงานพร้อมกันหลาย connection บนฐานข้อมูลจริง
