# แก้ความสอดคล้องระบบหลังบ้านสภา — 1 ตุลาคม 2569

## สถานะ

เตรียมโค้ดและ migration ในเครื่อง ยังไม่ได้อัปเดตฐานข้อมูลจริง, Edge Function หรือ deploy Vercel สำหรับชุดนี้

## รายการแก้

1. Calendar บันทึกกิจกรรมและผู้เข้าร่วมใน transaction เดียว ตรวจข้อผิดพลาดก่อนแสดงสำเร็จ
2. วันหยุด/วันเรียนแทนแยกข้อมูลที่กำหนดเองกับข้อมูลจากกิจกรรม คำนวณทั้งช่วงวันที่ใหม่เมื่อแก้หรือลบ และรักษาวันที่มีกิจกรรมซ้อนกัน
3. ค่าชำระสมาชิกใช้ RPC ล็อกแถวและแก้เฉพาะสมาชิกที่เลือก เก็บข้อมูลสลิปเดิม พร้อม audit ผู้เปลี่ยนสถานะ
4. ปิดใช้งานสมาชิกด้วย banned แทนลบบัญชีและประวัติ เครื่องมือตรวจประวัติไม่มีสมาชิกเป็นรายงานแบบอ่านอย่างเดียว นับบัญชีที่ถูกปิดใช้งานด้วย
5. สิทธิ์ฝ่ายต่าง ๆ ใช้นโยบายเดียวกับเซิร์ฟเวอร์: ฝ่ายที่รับผิดชอบ ประธาน และ admin
6. อาคารสถานที่และปฏิคมไม่มีปุ่มจัดการสำหรับผู้ไม่มีสิทธิ์
7. งบแยกตามปีการศึกษา และยอดอนุมัติแยกจากยอดจ่ายจริง บันทึกจ่ายผ่าน RPC ป้องกันจ่ายซ้ำและจ่ายเกินงบ
8. ผู้ขอ/อนุมัติ/จ่ายใช้ ID สมาชิก ชื่อเป็น snapshot; ชื่อซ้ำในข้อมูลเก่าไม่เดาว่าเป็นใคร
9. ประกาศในเว็บบันทึกผ่าน RPC ก่อนส่งภายนอก; Discord มีคิวถาวรและสถานะส่งซ้ำ แยกกรณีล้มเหลวกับไม่ทราบผลเพื่อเตือนข้อความซ้ำ
10. ชื่อหน้าและ breadcrumb อ่านเส้นทางจาก Router ให้ทำงานกับ HashRouter

## การตรวจ

- npm run build ผ่าน
- Deno check admin-users ผ่าน
- PostgreSQL จำลองด้วย PGlite ผ่าน 17 กรณี: วันหยุดหลายวัน/ซ้อนกัน/แก้ช่วงวัน, rollback ผู้เข้าร่วมผิด, สิทธิ์สมาชิก, ค่าชำระรายคน, เก็บ metadata สลิป, ย้อนสถานะรายคน, audit, อนุมัติไม่เท่ากับจ่าย, กันจ่ายซ้ำ, งบไม่ต่ำกว่ายอดจ่าย และผู้รับประกาศไม่ซ้ำ
- เปิดหลังบ้าน 27 หน้า ที่ความกว้าง 390 และ 1440 ด้วยข้อมูลจำลอง ไม่พบ pageerror, error boundary หรือ document overflow
- โมดูลใหม่ NotificationDeliveryStatus, discordWebhook, councilPermissions ผ่าน ESLint; ไฟล์เดิมยังมี lint debt ที่ไม่ใช่ syntax/no-undef
- ไม่ได้ทดสอบการส่ง Discord/Push จริง ไม่ทำรายการเงินจริง และไม่อ้างว่าทดสอบ concurrent หลาย connection แล้ว

## ขั้นตอนเปิดใช้

ใช้ migration `20261001180000_council_workflow_integrity.sql` และ deploy `admin-users` พร้อม frontend รุ่นนี้ในช่วงบำรุงรักษา: migration จำกัด direct write ของ events/event_participants และ finance เพื่อบังคับ transaction RPC จึงไม่ควรปล่อย frontend เก่าใช้งานร่วมหลัง migration

ก่อนเปิดให้ใช้จริง ตรวจงบเริ่มต้นแต่ละปี (ย้ายค่าเดิม 15,000 บาทมาเป็นค่าเริ่มต้น ไม่ใช่งบที่ยืนยันแล้ว) และรายการเก่าที่อนุมัติแต่เคยจ่ายแล้ว เพราะระบบไม่เดาวันจ่ายย้อนหลัง ให้ฝ่ายการเงินตรวจสอบก่อนบันทึกจ่าย

รายการวันเดิมไม่มี provenance: migration เก็บ snapshot ทั้งหมดใน `council_calendar_legacy_settings`; วันที่ทับช่วงกิจกรรมถือว่ามาจากกิจกรรมนั้น ส่วนวันที่อื่นเก็บเป็น manual ผู้ดูแลต้องตรวจวันซึ่งเดิมอาจตั้ง manual ทับกิจกรรมก่อนลบกิจกรรมเก่า

ชื่อผู้ขอ/อนุมัติเก่าที่ซ้ำกันไม่ถูกผูก ID อัตโนมัติ ผู้จัดการฝ่ายการเงินยังเห็นประวัติ แต่ผู้เรียน/สมาชิกไม่เห็นประวัติที่ยืนยันเจ้าของไม่ได้

สมาชิกที่ปิดใช้งานยังเก็บประวัติทั้งหมด สามารถคืนสถานะผ่านแก้ไขผู้ใช้และยกเลิก banned ได้

## การเปิดคิวแจ้งเตือน

ตั้ง `VITE_COUNCIL_NOTIFICATION_OUTBOX=true` หลัง migration สำเร็จเท่านั้น ค่าเริ่มต้นใช้ Apps Script โดยตรงและไม่เรียกตารางคิว ระหว่างนี้ยังไม่มีประวัติส่งซ้ำถาวร
